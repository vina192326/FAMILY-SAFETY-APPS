# Final product requirements — FAMILY SAFETY ONE APK

## App packaging and mode separation
- Exactly one Android application ID: `com.familysafety.app`; Parent, Kids and private Owner surfaces are separate navigation graphs within this APK.
- Preserve approved screen layouts, colors, typography, spacing, icons and interaction hierarchy. The uploaded Stitch HTML/PNG references are design source material; do not replace them with generic screens.
- No publicly visible text may say "Owner", "Admin", "Master Login" or expose an Owner credential entry. A neutral "Other" / "अन्य" entry may lead to a concealed authentication gesture or neutral settings page.
- Owner UI and data APIs require server-side Owner authentication. Hiding a button is not authorization.

## Parent Mode
- Opens Parent Dashboard directly. No email, username, password or account-registration form.
- A locally generated installation identity is registered with the backend and protected using Android Keystore-backed credentials. This is device identity, not a user login.
- Parent enters the OTP generated by the target Kids installation.
- OTP validation must succeed before the plan catalogue is returned.
- Plans show amount/currency, duration value and unit (minutes, hours, days, months or years), history-access period, and every included permission/capability.
- Linking is not active when an order is merely created, a payment app is opened, or a client says success.
- Device becomes linked only after server-side payment verification and Permit issuance.

## Kids Mode
- Free forever: no login, email, username, password, subscription, purchase or payment screen.
- Generates a random, short-lived OTP for Parent pairing. OTP is displayed only on the Kids device and is never hard-coded.
- Kids features that need permissions request them contextually and explain their use. A permission denial must not be disguised as granted.
- Reconnection uses the existing valid device binding and does not require repeated OTP entry.

## Permit invariants
- Every Kids installation/device binding has one distinct Permit ID.
- Permit records are unique, unguessable, server-issued and linked to exactly one Kids device.
- A Permit cannot be reused or transferred to a second Kids installation.
- Additional Kids devices require a new plan purchase and new Permit.
- Permit activation and device binding occur in one database transaction after verified payment.
- Reconnection is allowed while the binding and Permit are valid and not revoked/expired.
- Expired/revoked Permit requires a new purchase; it does not silently fall back to a free paid-feature state.

## Payment verification
- Use a real gateway server integration. Razorpay is the initial adapter; credentials are supplied through deployment secrets.
- Create orders on the server; validate order/payment IDs and gateway signature; independently fetch payment status from gateway and require captured/paid status and exact amount/currency/order match.
- Webhook signatures are verified using the webhook secret. Process events idempotently.
- UPI intent handoff, app chooser return values, screenshots, client-side flags and manually entered UTRs are not authoritative proof.
- If gateway credentials are absent, paid linking remains unavailable and clearly reports configuration failure. Never simulate success.

## Owner access
- Neutral entry only; no public Owner/Admin/Master Login labels.
- Owner authentication is server-verified. Password is mandatory; User ID is optional. A correct configured Permanent Master Password alone may authenticate. Every failed credential combination returns exactly `Invalid User ID or Password.`. Password hashes are stored with BCrypt; plaintext passwords are never embedded in APK/source code.
- Owner APIs require a separate short-lived Owner session and role checks. Parent/Kids tokens cannot call Owner endpoints.
- Rate limit and audit failed/successful Owner authentication.

## Security and privacy
- TLS required outside local development.
- Store only hashes of bearer tokens and OTPs; OTP expires quickly and is rate-limited.
- Use cryptographically secure random values; never log OTP, bearer token, payment secret or TOTP seed.
- Use PostgreSQL transactions and uniqueness constraints to prevent double spending, duplicate Permit issuance and race-condition linking.
- Parent/Kids mode separation is UI/navigation separation, not a security boundary; backend authorization is authoritative.
